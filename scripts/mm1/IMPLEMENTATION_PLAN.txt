US-align -mm 1 with -dir/-dir1/-dir2 Mode Adaptation Plan
========================================================

Based on an in-depth analysis of the US-align source code architecture, this document presents a complete implementation plan. The changes are divided into three progressive phases (-dir1 -> -dir2 -> -dir), each containing 5 detailed steps, ensuring every step is verifiable and regression-testable.

I. Requirements Background and Objectives

1.1 Business Background
US-align's -mm 1 mode (oligomeric/multi-chain complex alignment) and -dir/-dir1/-dir2 modes (directory batch alignment) are both core features. However, two issues currently exist:
- -dir and -mm 1 are hard-coded as mutually exclusive (USalign.cpp:3459), preventing their combined use
- -dir1/-dir2 with -mm 1 are not blocked, but MMalign merges all files in the directory into one giant complex, producing incorrect results

1.2 Objectives
- Implement -dir1 + -mm 1: each complex in the directory vs a specified target complex
- Implement -dir2 + -mm 1: a specified query complex vs each complex in the directory
- Implement -dir + -mm 1: all-vs-all comparison of all complexes in the directory (upper triangle)
- Ensure existing monomer -dir, -dirpair, and single-pair alignment logic remain unaffected

II. Core Pain Points and Root Cause Analysis

Key differences between MMalign and TMalign:

                        TMalign                         MMalign
Parsing                 get_PDB_lines (per file)        parse_chain_list (merge all files)
Looping                 Internal i/j double loop        No loop, all merged into one comparison
-dir                    Each file parsed individually   All files merged -> giant complex
                        -> pairwise comparison           -> incorrect result

parse_chain_list (MMalign.h:1077) logic:
    for each file in chain_list:
        parse all chains in that file -> append individually to xa_vec/ya_vec
So passing [a.pdb, b.pdb, c.pdb] creates one giant complex containing all chains from all three files.

Correct approach: add an outer loop in the main function, passing only single file pairs to MMalign each time.

Three modes, chain_list structure and traversal:

Mode                        chain1_list                             chain2_list             Traversal
-dir1 PDB/ list target      [PDB/a.pdb, PDB/b.pdb, PDB/c.pdb]       [target.pdb]            Single loop over chain1_list
query -dir2 PDB/ list       [query.pdb]                             [PDB/a.pdb, PDB/b.pdb, ...]  Single loop over chain2_list
-dir PDB/ list              [PDB/a.pdb, PDB/b.pdb, PDB/c.pdb]      Same as chain1_list      Upper triangle double loop (ii<jj)

Prefix stripping parameter reference (MMalign internally uses xname.substr(dir1_opt.size()) for stripping):

Mode        xname example    yname example      dir1_opt passed    dir2_opt passed
-dir1       PDB/a.pdb        target.pdb         dir1_opt           ""
-dir2       query.pdb        PDB/a.pdb          ""                 dir2_opt
-dir        PDB/a.pdb        PDB/b.pdb          dir_opt            dir_opt

III. Development Workflow: Phased Delivery on Usalign-beta Branch

Overall strategy: After completing coding and compilation for each feature, pause and notify the developer to perform manual testing. Once the developer confirms the tests pass, proceed to the next feature adaptation. This ensures a human verification checkpoint at every step.

Detailed workflow:
1. Create the Usalign-beta directory
   Copy all source files (.cpp, .h, Makefile, etc.) from the USalign-master directory to the Usalign-beta directory.
   All subsequent code modifications are made in Usalign-beta; the original USalign-master directory remains unchanged.

2. Three-phase progressive development:
   Phase 1 (-dir1 + -mm 1):
     a. Coding complete -> compilation passes -> notify developer for manual testing
     b. Developer runs manual tests per the verification matrix (Step 1.5)
     c. Tests pass -> commit changes to Usalign-beta -> proceed to Phase 2

   Phase 2 (-dir2 + -mm 1):
     a. Coding complete -> compilation passes -> notify developer for manual testing
     b. Developer runs manual tests per the verification matrix (Step 2.5, including -dir1 regression)
     c. Tests pass -> commit changes to Usalign-beta -> proceed to Phase 3

   Phase 3 (-dir + -mm 1):
     a. Coding complete -> compilation passes -> notify developer for manual testing
     b. Developer runs manual tests per the verification matrix (Step 3.5, including -dir1/-dir2 regression)
     c. Tests pass -> commit changes to Usalign-beta -> all feature adaptations complete

3. Each phase deliverables:
   - Modified source code (in Usalign-beta directory)
   - Compiled executable USalign (or USalign.exe)
   - Verification matrix for the current phase, for developer item-by-item review

IV. Detailed Implementation Plan (Three Progressive Phases)

=============================
Phase 1: Implement -dir1 + -mm 1
=============================

Current status: -dir1 + -mm 1 is not blocked, but MMalign merges all files in chain1_list into one giant complex, producing incorrect results.

Step 1.1: Confirm no need to remove blocking
The current blocking check (USalign.cpp:3459) only targets dir_opt:
    if (dir_opt.size() && (mm_opt==1||mm_opt==2))
        PrintErrorAndQuit("-mm 1 or 2 cannot be used with -dir");
-dir1 is not affected by this check, so no modification to the blocking logic is needed.
The current code enters the mm_opt==1 branch via the if (dirpair_opt.size()==0) path (USalign.cpp:3534), passing the entire chain1_list to MMalign -> merged into a giant complex. This is what needs to be fixed.

Step 1.2: Add safety guardrails
After USalign.cpp:3488, add a mutual exclusion check for -chainmap with -dir1:

    if (chainmapfile.size() && mm_opt!=1)
        PrintErrorAndQuit("ERROR! -chainmap must be used with -mm 1");
    // New:
    if (chainmapfile.size() && dir1_opt.size())
        PrintErrorAndQuit("ERROR! -chainmap cannot be used with -dir1");

Step 1.3: Add -dir1 loop entry point in mm_opt==1 branch
In USalign.cpp:3534-3536, insert the -dir1 branch entry before the existing if (dirpair_opt.size()==0).

Current structure:
    else if (mm_opt==1)
    {
        if (dirpair_opt.size()==0) MMalign(...)  // original single-pair path
        else { ... }                               // original -dirpair path
    }

Modified to:
    else if (mm_opt==1)
    {
        if (dir1_opt.size()>0) { ... }            // new -dir1 path
        else if (dirpair_opt.size()==0) MMalign(...)  // original single-pair path unchanged
        else { ... }                                   // original -dirpair path unchanged
    }

Step 1.4: Implement -dir1 loop body
    else if (dir1_opt.size()>0)
    {
        // -dir1: each complex in directory vs target
        for (int ii=0; ii<chain1_list.size(); ii++)
        {
            xname = chain1_list[ii];
            yname = chain2_list[0];
            vector<string> single1(1, xname);
            vector<string> single2(1, yname);
            MMalign(xname, yname, fname_super,
                fname_lign, fname_matrix, sequence, d0_scale, m_opt, o_opt,
                a_opt, d_opt, full_opt, TMcut, infmt1_opt, infmt2_opt,
                ter_opt, split_opt, outfmt_opt, fast_opt, mirror_opt, het_opt,
                atom_opt, autojustify, mol_opt, dir1_opt, "",
                chain2parse1, chain2parse2, model2parse1, model2parse2,
                single1, single2, byresi_opt, chainmapfile, se_opt);
        }
    }

Key design points:
- xname = chain1_list[ii]: full path like PDB/a.pdb; MMalign internally uses xname.substr(dir1_opt.size()) -> a.pdb
- yname = chain2_list[0]: bare filename like target.pdb; dir2_opt="" so no stripping
- single1/single2: single-element vectors; parse_chain_list parses only one file -> no multi-file merging

VII. Known Limitations

1. Error handling: MMalign internally uses PrintErrorAndQuit (exit(1)), so a single corrupted file terminates the entire batch job.
   This release does not modify MMalign's internal error handling (impact scope too large). Users should ensure files in the directory have correct formats.

2. Performance: No file parsing cache; each file is re-parsed for every comparison pair. Impact is negligible for small directories (N < 30).

3. -full option: In directory mode, this produces extremely verbose output (per-chain detailed comparison for every pair). Combining with directory mode is not recommended.
